# Architecture and domain overview

This page maps the implemented eeebot product, its bounded self-evolving runtime, and the principal authority boundaries.

## Product identity and package layout

`eeebot` is the product and public identity. The implementation and internal imports use `nanobot.*`; `eeebot/` is the external compatibility layer. Both `nanobot` and `eeebot` CLI entry points are intentional package contracts. See [[README.md]], [[pyproject.toml]], [[nanobot/cli/commands.py#main]], and [[nanobot/cli/eeebot.py#main]].

The repository also contains the constrained self-evolving runtime and host release tooling; it is not merely the chat-agent framework. Capability truth is organized under [[docs/specs/README.md]]. The separate operations dashboard repository is not the canonical product runtime.

## Two runtime surfaces

The package supports an operator-facing chat framework and a separate bounded host runtime.

### Operator-facing chat framework

The chat framework exposes channels, tools, model routing, and user sessions through the CLI and agent package. It is distinct from the timer-driven host runtime. Shared package code does not make the two execution authorities interchangeable.

### Bounded self-evolving bridge

The host bridge runs a bounded cycle through planning, subagent execution, gates, and evidence recording.

The entry point is [[nanobot/runtime/bridge.py#main]]. A cycle collects demand and proposer candidates before planner selection; a no-plan/rest result does not start the executor. Planned work proceeds through isolated subagent execution, gates, and evidence recording. The bridge chooses whether an accepted result can be integrated; executor output is not itself authority to change the product repository.

The planning session is implemented by [[nanobot/runtime/bridge.py#_run_planning_session]]. It receives demand candidates collected by [[nanobot/runtime/demand.py#collect_demand]] and proposer candidates from [[nanobot/runtime/llm_proposer.py#proposer_candidate_items]], then returns a plan or an explicit no-plan/rest outcome. The normal `no_plan`, validated `rest`, and unchanged-rest precheck returns carry a bounded in-memory `terminal_outcome` for the bridge caller; this is classification only, not a durable owner receipt. Refusal, malformed, spawn/provider failure, cancellation, and unexpected exceptions remain without that field so an absent plan cannot imply a confirmed no-execution result. The executor task is derived from the planner's plan; a candidate is optional context, not a task assignment. Do not infer a no-demand idle rule from older architecture prose without checking current code and configuration. See [[planning]] for the candidate/selection boundary.

[[OPERATING.md]] exempts an executor-discovered already-done or inapplicable skip from the closing diary line and further tool calls; other executor outcomes retain the diary obligation. Before executor start, the harness attempts an opening entry that records the task, not the later outcome. The status-aware instruction test [[tests/test_operating_md.py#test_executor_skip_diary_exception]] checks both contract branches with positive and negative fixtures; ADR-053 is the provisional decision in this candidate.

The LLM proposer can author bounded candidates through [[nanobot/runtime/llm_proposer.py#maybe_propose]]. It is a candidate/request source, not the planner. Planner selection and proposer authoring are related but distinct steps, and an idle, failed, rested, blocked, or unplanned cycle is not an executed task. The bridge gives proposer authoring its own durable route-parent owner; OpenAI HTTP request/response hooks record physical SDK dispatches without changing SDK or bounded fallback retry budgets, and unknown transport settlement holds that proposer owner. Autonomous goal review uses the planner-owned route when `demand.collect_demand` recomputes the scorecard. The `bridge.cycle` parent route is separate from planner/executor identities. Normal explicit `no_plan`, validated `rest`, and `rest_unchanged` outcomes may close that owner through a separate no-execution receipt only when no phase or provider/tool attempt was admitted. A conclusively detected exact-tag, recent-failure, or existence-index duplicate instead records the distinct duplicate outcome allowed by [[nanobot/runtime/intent_journal.py#_BRIDGE_NO_EXECUTION_OUTCOMES]] on that same receipt before returning; the empty-owner rule rejects any attempt/phase or unknown effect, and the receipt neither settles planner/proposer operations nor changes open-increment retry state. The two-invocation regression verifies a genuine duplicate starts no executor and does not strand the next legitimate cycle; the companion journal test verifies an attempted owner cannot receive that receipt. See [[tests/test_cycle_ledger.py#TestBridgeIntegrationLedgerRows#test_real_duplicate_closes_empty_owner_before_next_legitimate_invocation]] and [[tests/test_intent_journal.py#test_duplicate_suppressed_receipt_cannot_settle_unknown_attempt_owner]]. Successful single-candidate integration binds `post_execution`, the exact smoke-tested head, and the integration helper receipt to the checkpoint, then closes the selected prefix against exact receipts. Non-integration paths close only the exact checkpoint-complete prefix they reached; omitted phases remain unmet. Reflection remains deferred to its separate timer owner.

Under `main()`'s existing lock, [[nanobot/runtime/intent_journal.py#read_route_parent_state]] reads the selected route's validated lifecycle without mutating it. An uninitialized or validated closed route may begin a new owner; a provisioned owner that has not started is reused. A started owner is closed and rotated only after either a clean, owner/cycle-bound completed integration checkpoint prefix is read back and its exact phase heads are reconciled, or a matching explicit normal no-execution receipt is verified. Verified incomplete `post_execution`/`smoke_gate` prefixes, unresolved attempts, a running/missing/mismatched checkpoint, or corrupt/incomplete route remain held on the same owner before proposer/planner work. The planner's persisted `stopped` guard is checked before stale-attempt recovery and bridge-cycle owner admission, so a stopped no-op does not rewrite open-increment recovery evidence or create a new owner; operator resume can reach a later ordinary invocation. This does not settle or rotate any pre-existing started/unknown owner. The snapshot alone never authorizes another effect. This recovery does not grant retry authority: executor failures currently leave the checkpoint running, so #1280/#1765 retry progression remains blocked until separately approved exact-attempt settlement is available. The production executor manager receives this cycle owner only for provider/tool operation intents; HTTP transport hooks record each physical SDK send and unresolved sends keep the cycle owner held across restart. This evidence does not settle or reoffer the executor task. Checkpoint verification stays with the caller; #2180 does not mint executor task identity or change #2162 ownership. Embeddings and interactive agent calls are not covered by these autonomous route tests. See [[nanobot/runtime/bridge.py#main]], [[nanobot/runtime/intent_journal.py#bridge_cycle_parent_context]], [[nanobot/runtime/phase_checkpoint.py#begin_phase]], and [[docs/adr/ADR-058-execute-cycles-as-checkpointed-phases-with-step-memos.md]].

The standalone [[nanobot/runtime/reflector.py#run_reflector]] selects completed cycles after its persisted watermark, appends each reflection to its journal, then advances the watermark. If one exact complete result row was appended but the cursor was not, restart validates its bounded shape and advances without repeating the model call; the existing [[nanobot/runtime/reflector.py#mark_reflection_consumed]] writer may mark a parent row consumed without a parent timestamp only after all its recommendations are consumed, which remains valid completion evidence. Ambiguous, conflicting, malformed, or unframed journal evidence holds before model dispatch, cursor change, or reanchor diagnostics, including when later cycles are otherwise eligible. A watermark cycle is retried only with positive retained `skipped_pruned` evidence and a returned transcript; an absent result row alone never rewinds a known cursor. A completed result after an earlier completion is ambiguous. This is reflector-local bookkeeping, not bridge phase or owner authorization, and does not cover a crash before result persistence. Tests cover the A/B crash window, writer-produced consumed-parent recovery, skip/error/retry order, and no replay from cursor plus transcript alone. See [[tests/test_reflector.py#test_reflector_consumed_last_recommendation_recovers_on_next_process]], [[tests/test_reflector.py#test_reflector_recovers_result_appended_before_watermark_after_process_exit]], [[tests/test_reflector.py#test_reflector_ambiguous_prior_result_holds_without_cursor_advance]], [[tests/test_reflector.py#test_reflector_skipped_then_error_then_retry_can_recover]], [[tests/test_reflector.py#test_reflector_known_cursor_without_result_does_not_replay_from_prompt_alone]], and [[tests/test_reflector.py#test_reflector_holds_ambiguous_watermark_before_later_cycle_max_limit]].

The planner persists a rest wake condition, observed-input version, and deadline; the bridge's existing precheck holds before the deadline when the input is unchanged, and permits the normal guarded cycle path at the deadline. The focused test writes the rest state in one interpreter and verifies pre-deadline hold and deadline eligibility from fresh interpreters, then checks that bridge entry before the deadline does not dispatch proposer, planner, or executor. It does not test a real systemd timer firing, wall-clock waiting, or host restart behavior. See [[nanobot/runtime/planner_rest.py#record_rest]], [[nanobot/runtime/planner_rest.py#precheck]], and [[tests/test_cycle_ledger.py#TestBridgeIntegrationLedgerRows#test_persisted_rest_precheck_blocks_until_deadline_across_restart]].

The public derived-view producer serializes goal-review-owned derived-priority rows with explicit `self-derived` provenance; operator priority wording remains private and the external typed dashboard allowlist is a read-only consumer. See [[nanobot/runtime/demand.py#build_derived_view]], [[docs/specs/subagent-bridge/spec.md]], and [[docs/adr/ADR-048-persist-self-derived-provenance-in-public-projection.md]] (Proposed).


## Intent-before-effect evidence

ADR-056 is effective; the current code and tests establish only selected autonomous provider and tool paths, not its full route inventory or replay contract.

The planner route provisions opaque parent ownership before effects and persists a start marker before its first planner dispatch. Restart reloads the same token; a started parent that is not durably consumed stays held, even if individual attempts have terminal or consumption records. Planner provider retries and tool dispatches record distinct durable intent, terminal, and consumption events without changing existing budgets or prompt bytes. Parent closure and settled-owner markers are written before rollover; bounded retention refuses new parents rather than evicting old evidence. A failed close never releases a planner result. The journal grants no replay permission. The LiteLLM provider supplies a per-call OpenAI SDK client for journal-enabled routes only when LiteLLM confirms the effective call model uses its direct OpenAI path; unsupported route overrides fail closed. HTTP hooks record physical SDK sends inside the same journal operation, preserving confirmed-response SDK retry budgets and holding on response-less settlement. Nonjournal LiteLLM calls use the normal library path. The planner-manager integration test injects an owner; this does not wire the production bridge executor manager, which does not receive `intent_state_root`/`intent_owner_id` and remains under #2162 for task/attempt identity and recovery. The bridge's proposer `maybe_propose` route has a route parent and hooks for primary/fallback SDK calls; `propose_many` and direct `propose` calls outside that parent are not established as covered. Other direct OpenAI SDK callers in `knowledge_lift`, `knowledge_curator`, `persona_harness`, `reflector`, `skill_eval_harness`, and `strategist` are not journal-wrapped. Provider calls in memory, heartbeat and evaluator paths have no route owner wiring shown here. Goal-review provider calls made during bridge demand collection can run under the active planner or proposer journal owner; direct goal-review calls outside those parent contexts are not established as covered. Generic interactive turns and remaining uncovered routes do not inherit planner coverage. See [[nanobot/runtime/intent_journal.py#provision_route_parent]], [[nanobot/runtime/intent_journal.py#bridge_parent_context]], [[nanobot/runtime/intent_journal.py#close_route_parent]], [[nanobot/runtime/intent_journal.py#operation_context]], [[nanobot/providers/base.py#LLMProvider#chat_with_retry]], [[nanobot/providers/litellm_provider.py#LiteLLMProvider#_journaled_openai_client]], [[nanobot/agent/subagent.py#SubagentManager#_run_subagent]], and [[tests/test_provider_retry.py#test_litellm_per_send_guard_preserves_known_retry_and_holds_lost_response]]. The executor lost-response regression now exits after a real mocked provider send, then runs bridge entry in a separate interpreter without owner injection and verifies the expected journal hold, unchanged journal/parent bytes, and one observable send across both processes; its Windows lock/fsync shims prove logic behavior only, not power-loss durability. See [[tests/test_cycle_ledger.py#TestBridgeIntegrationLedgerRows#test_executor_provider_attempt_uses_bridge_cycle_owner]]. A separate regression distinguishes failure to admit the initial bridge-cycle owner (which holds before proposer) from failure to admit the proposer route parent after that owner exists; the latter records `proposer_intent_held` and still does not dispatch the planner. See [[tests/test_bridge_bulk_skip.py#TestSingleCandidatePerCycle#test_proposer_journal_admission_failure_holds_before_planner]].

The journal rejects malformed or oversized owner files without resetting them, uses fixed metadata allowlists and per-owner limits, and requires supported locking and sync before use. Closed route snapshots and the route-provisioning capacity scan both require each settled-owner marker to have the exact shape and a parseable timezone-aware ISO timestamp; a malformed marker blocks new owner admission without rewriting existing state. Missing or malformed closure evidence, including a leftover route marker without its pointer, remains held by [[nanobot/runtime/intent_journal.py#_verify_settled_route_parent]], [[nanobot/runtime/intent_journal.py#_settled_route_owners]], and [[nanobot/runtime/intent_journal.py#read_route_parent_state]]. Tests cover metadata validation, ownership and capacity bounds, injected file- and directory-sync failure, child termination, stale temporary files, and persistent lock identity. The Windows development suite uses a fake lock only for logic tests and separately verifies that the real implementation fails closed because required locking and directory sync are unavailable; POSIX durability requires POSIX-host evidence. The injected post-replace terminal-directory-sync failure leaves a complete `intent` plus `terminal` visible to the running process, but the append API withholds success; this is not evidence of restart durability after that sync failure.

## Evidence, gates, and authority

Cycle and phase evidence is append-oriented in the runtime ledger at [[nanobot/runtime/cycle_ledger.py#append_event]]. Demand collection and ranking provide inputs; they do not establish that work passed a gate or integrated.

The role-based prompt provenance matrix also exercises goal review and demand-mode proposal at their real SDK dispatches; the operator-facing AgentLoop is covered through message assembly and provider retry dispatch. Selected prompt producers also attach bounded actual-call section provenance to existing LLM telemetry. Assembly metadata remains reusable only within its bounded owner context so retries/fallback dispatches retain the producer while separate owners cannot cross-correlate identical prompt bytes; ownerless provider calls use isolated baseline identity. A reflector job shares one owner window across its selected cycle prompts and resets for its next invocation; curator retry batches likewise share one job owner, while later curator, strategist, and narrator invocations receive fresh owner windows. `cycle_id` remains separate telemetry attribution. This is process-local comparison evidence, not a trust anchor or proof of provider receipt. See [[docs/specs/observability/spec.md]].

The existing `cycle-health` summary reports warning or UNKNOWN from exact keyed start/outcome ledger evidence. The cycle-progress reader passes its single reference instant into both progress bounds and the ledger retention check, so deterministic historical reads do not become partial solely because the machine clock is later. Byte-capped or genuinely expired windows remain partial/UNKNOWN; malformed JSON field types or empty identifiers, future-dated/naive timestamps, missing active ledger with archive-only evidence, and incomplete reset coverage are UNKNOWN; valid unrelated phases are ignored without weakening malformed success-shaped-row checks. Because the ledger has no global inception/completeness watermark, a retained window cannot prove no older task keys were pruned, so below-threshold aggregate status remains UNKNOWN. Strict H5 ledger reads reject invalid UTF-8 rather than replacing corrupted key bytes; valid Unicode U+FFFD remains accepted. Same-key keep/resume attempts may repeat a cycle ID and each started row counts; a later duplicate skip for that reused ID is ambiguous even with a supplied matching key and produces UNKNOWN. Duplicate-skip subtraction otherwise requires an exact unique cycle/key join; mismatched, unjoined, or repeated joins produce UNKNOWN. See [[evidence]] for evidence status and fitness boundaries.

A subagent works in a cycle-scoped branch through [[nanobot/runtime/bridge.py#_setup_cycle_branch]]. The bridge applies the bounded smoke and mutation-surface checks before integration. Runtime-slice changes are promotion candidates for operator review rather than ordinary script-tier auto-integration; see [[gates-and-promotion]], [[docs/specs/subagent-bridge/spec.md]], and [[docs/specs/promotion-and-release/spec.md]].

The fitness boundary is harness-owned: scorecard and held-out verification are product-side evidence, outside the instance's writable workspace. The instance cannot define or edit its own fitness checkers. See [[nanobot/runtime/scorecard.py#compute_scorecard]], [[docs/specs/self-evolving-runtime/spec.md]], and [[docs/specs/promotion-and-release/spec.md]].

## State and deployment boundaries

Code, mutable instance workspace, runtime state, and product release are separate authority domains.

`nanobot/runtime/phase_checkpoint.py` provides a strict, bounded versioned checkpoint for one bridge cycle under `state/subagent_bridge/`; `bridge._evaluate_candidate` wires it into the selected integration path. At `post_execution` admission the bridge reads the verified retained cycle-branch tip through [[nanobot/runtime/phase_checkpoint.py#verified_local_branch_tip]], while keeping the original integration base in `base_sha`. Completion receives that same admitted tip and may advance the checkpoint head only to a clean committed descendant on the same cycle branch; a wrong checkout, unrelated/repointed tip, or uncommitted output is held. Before integration it verifies the exact local cycle branch, base ancestry, and head. `smoke_gate` completion requires an explicit pass tied to that exact head and a clean tree; integration admission rechecks the branch head so later commits invalidate the gate receipt. Integration completion then requires the successful bridge receipt plus the retained cycle ref, local and tracking `main`, cycle trailer, and exact merge parents. The following `reflection` phase revalidates that integration evidence. Corrupt state (including a dangling checkpoint symlink), an unresolved phase, or owner/revision/receipt mismatch is held rather than treated as empty. A new cycle may replace the retained checkpoint only after every declared phase of the prior cycle is complete, regardless of whether the caller-supplied owner token changes. In production, smoke and integration receipts are persisted by `complete_phase`; the generic first-write `memo` helper has no production caller. Restart recovery reconciles a completed integration prefix and closes its owner, while running or incomplete prefixes remain held before dispatch; this is not same-cycle phase resumption or authorization to repeat an effect. The bridge success test exercises production receipt writes; a process-restart regression stops after the real merge-and-push effect, then verifies the checkpoint, receipt recovery and owner closure on a fresh bridge invocation without a second integration or push. Phase-machine tests separately exercise generic memo persistence and stale-evidence rejection; the generic first-write `memo` helper remains without a production caller. The retained-tip caller tests verify distinct integration-base and branch-tip identity, refusal on a wrong checkout, and a held checkpoint when the retained ref is shifted to a non-descendant; see [[tests/test_cycle_phase_machine.py#test_bridge_post_execution_admits_retained_tip_without_replacing_integration_base]], [[tests/test_cycle_phase_machine.py#test_bridge_post_execution_rejects_wrong_checkout_before_admission]], [[tests/test_cycle_phase_machine.py#test_post_execution_completion_rejects_wrong_checkout_without_advancing]], and [[tests/test_cycle_phase_machine.py#test_post_execution_completion_rejects_non_descendant_retained_tip_shift]]. These checkpoints do not replace best-effort append evidence in `cycle_ledger.py` or executor-call recovery ownership.

The self-evolving instance workspace is where bounded cycle changes are staged and integrated. Runtime state is held separately under the configured state root; it is evidence and operational state, not a second source-code repository. Product releases are selected through the host release mechanism and verified separately from repository CI. This page makes no claim about current host installation or health. See [[host-boundaries]], [[docs/specs/host-runtime/spec.md]], [[docs/specs/subagent-bridge/spec.md]], and [[docs/CURRENT_ARCHITECTURE.md]].
