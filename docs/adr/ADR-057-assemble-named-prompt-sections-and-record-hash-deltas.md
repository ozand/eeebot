# Status

Provisional accepted candidate; not yet effective or implemented. Governing design for `#2179`. Under the delegated technical delivery authority recorded in #2179, this candidate is submitted for independent review and applicable checks. If it passes on this exact revision, acceptance is planned through the authorized unchanged merge of its #2179 PR under the repository ADR lifecycle. No implementation may proceed before that effective-acceptance event.

# Context

`ContextBuilder` assembles interactive and loop-profile prompts from ordered sections; `role_prompt` separately assembles named runtime-role prompts. `ADR-046` records resolved prompt budgets but not per-section change provenance. Existing telemetry correlates rows with `cycle_id`, `component`, and a process-local `seq`; that sequence is not a durable or unique call identity. Named sections may reveal approved changes and may enable provider prefix caching, but cache benefits and current byte/order behavior must be measured rather than assumed. #2058 separately owns a reserved trust-boundary decision for selected-ref exporter execution and approved provenance; this proposal does not authorize, implement, or supersede that trust work. Prompt provenance describes the system message only, not the full request, user message, tool payload, or provider transport attempts.

# Decision

1. Represent the in-scope system-prompt builders as ordered named sections while preserving the exact emitted system-message bytes and section order in the first implementation. Preserve the existing string API and fitting behavior. Provenance emits names and relative order only for explicitly allowlisted safe sections, in their filtered sequence; omitted sensitive sections do not create placeholders, original-position numbers, gaps, counts, or other signals that reveal their presence or rank. Do not reorder sections to create a static prefix. Any later reorder requires a separately reconciled behavior change, byte-level verification, and provider-specific measurement before claiming cache benefit.
2. After successful prompt assembly and immediately before dispatch to the provider interface or direct SDK client, create an opaque random `call_id` once per logical application-level provider invocation. Do not assign it to a prompt-builder refusal that never reaches that boundary. The ID correlates that invocation's prompt provenance and applicable existing call, prompt, and bounded failure telemetry; it is not `cycle_id`, process-local `seq`, a physical network-attempt ID, an idempotency key, or proof the provider received or served the request. Internal transport retries within the invocation share the ID; no retry-count or delivery semantics change. Provenance describes the actual system-message bytes supplied to the provider interface. If an implementation retries with a changed system message, the record must reflect the actual supplied system message or report provenance unavailable, not claim a single unchanged prompt. An ID alone does not establish provider admission; if no provider-interface invocation occurs, no provider call/failure/provenance row is fabricated. Cancellation after dispatch may leave no completion or prompt-capture row; this is unavailable evidence, not proof the provider did not receive or process the request. Do not add a terminal/intent protocol or fabricate a completion row for that case.
3. A bounded in-memory baseline is scoped to a prompt producer/schema within one runtime owner window: an interactive logical session plus separate interactive and loop-profile `ContextBuilder` schemas; one bridge cycle with separate planner-role, executor-loop, and repair-loop schemas; or one standalone role-job invocation. Baseline identity includes an opaque producer/schema identifier, so a planner prompt is never compared with executor prompt sections merely because both occur in the same cycle. A repair executor uses the executor-loop baseline only when its section schema is identical; otherwise it starts a fresh baseline. Generic fixed-role `SubagentManager` prompt bypass callers are excluded from this contract and producer inventory. A baseline starts at first observed system-prompt dispatch. Each subsequent provider invocation records only deltas against the immediately preceding snapshot in that same owner and producer/schema baseline, including `previous_call_id` to identify the comparison predecessor. Owner invocations sharing a baseline must serialize snapshot compare/update; concurrent unrelated owners must not share a baseline. The in-memory cache holds at most 64 owner/producer baselines; least-recently-used eviction discards the baseline, and the next invocation starts a new opaque `baseline_id` with a full snapshot. Process restart, cache miss, schema change, a changed caller-supplied runtime release identifier, or a transition between identified and unidentified release state starts a fresh baseline; repeated absence of a release identifier within the same live owner/schema does not reset it. Use only the existing runtime release identifier where the caller already provides it. This value is attribution only, not an authenticated source SHA; do not inspect Git or resolve selected refs to obtain it. A reset never reconstructs or infers a missing prior baseline. Provenance carries a snapshot/delta kind and predecessor linkage, so a reader that lacks the referenced predecessor treats the delta history as unavailable, not complete. One-shot roles legitimately have a single snapshot. Baseline IDs and call IDs are opaque correlation values, not identities, authentication, or trust anchors. No cross-process persistence, restart continuity, replay, terminal-write protocol, database, or new execution framework is introduced.
4. Compute deterministic UTF-8 `sha256` digests and character lengths only for explicitly allowlisted, non-sensitive sections approved for that evidence surface. Before enabling any digest, the implementation must enumerate exact section producers/files or generated constants and independently justify each as non-sensitive; a section name alone never implies safety. If no section meets that classification, emit no section digests. The allowlist does not automatically admit new or changed sections. Provenance emits safe names and their relative order only as a filtered sequence; omitted sensitive sections cannot affect emitted positions, gaps, counts, or ordering signals. Unknown sections default to sensitive and are omitted. Omit sensitive/private/operator-priority, goal, workspace, memory, task, and runtime-derived material without any content-derived digest, length, delta, name, presence, count, position, gap, or order signal. Hashes of guessable text can disclose content by dictionary testing and equality correlation. Append provenance only as optional, bounded fields to existing runtime `llm_calls` duration, prompt, and applicable bounded failure records; the complete provenance object is capped at 8 KiB, contains at most 32 safe section entries with bounded fixed names/digests, and is omitted if it cannot fit. If provider failure lacks an actual system-message observation, record only bounded attempt correlation and mark section provenance unavailable; do not fabricate a snapshot. Do not add a cycle-ledger row or expose this metadata through dashboard/public projections. Do not claim this metadata creates filesystem access control or proves the existing telemetry files are private. Existing raw prompt capture policies, destinations, and retention are unchanged; no raw prompt or private input is added to provenance.
5. Bind permitted provenance to schema version, observed safe-section order, and the existing runtime release identifier when available. The release identifier is optional attribution only, not an authenticated source SHA. When absent, omit release attribution; repeated absence does not invalidate an otherwise live owner/schema baseline. Missing baseline means unavailable/reset, not an empty prompt. A digest is comparison metadata, not authentication, authority, or reconstruction. This proposal does not resolve #2058's selected-ref exporter trust boundary: it neither chooses a trust anchor nor makes a hash authenticate exporter code or metadata.
6. Cover production consumers of `ContextBuilder` (interactive loop and loop-profile executor) and the named autonomous role builders/callers: proposer/demand-proposer/goal-review, planner, reflector, strategist, curator, and narrator. Inventory their actual call and telemetry paths before implementation; tests must cover each selected production path. Do not claim that every generic LLM caller, evaluation harness, persona fixture, or arbitrary provider invocation is covered unless explicitly included and tested. Any excluded path is named with its reason and does not count as covered.
7. Preserve `ADR-022`'s 15,500-character pool cap, ontology order and budgets, and `ADR-046` budget fields; no mid-conversation provider wire-format dependency on unsupported gateways. This ADR does not alter #2058's reserved exporter/trust-anchor scope or requirement for explicit operator decisions. It also does not absorb #1930/#2021 compaction corrections or the `#1989` recovery regression.

# Consequences

### Easier

For explicitly approved non-sensitive sections, operators can compare bounded changes within one runtime owner window and correlate them to a logical provider invocation. Restart resets the comparison window; no historical reconstruction or cross-process continuity is claimed. This does not identify sensitive section content, prove provider receipt, or prove cache behavior. Gateway-specific cache benefit remains a hypothesis requiring measurement; hashes cannot reconstruct unavailable historical text.

### Harder

In-scope builders and call sites must preserve current emitted bytes while exposing a bounded internal representation and correlating actual system-message provenance to logical calls. Per-owner in-memory baseline lifecycle, opaque IDs, sensitive-section omission, legacy-compatible optional telemetry, and producer coverage add implementation and verification cost. Missing telemetry/provenance remains unavailable and must not block the model call.

### What does not change

`ADR-022` file ownership and ontology ordering, the 15,500-char release pool cap, `ADR-046` resolved budget fields, and operator-priority privacy rules remain unchanged. Existing telemetry and prompt records remain readable; new provenance fields are optional/additive and missing legacy fields mean unavailable. No host access, activation, provider call, or public projection change is authorized.

# Alternatives considered

- **Store full rendered system prompts on every ledger row:** rejected due to storage bloat on `eeepc` and private operator-priority exposure risk.
- **Hash only the concatenated prompt string:** rejected because a single digest hides which input section drifted.
- **Persist baselines across restarts or reuse prompt-capture files:** rejected; current prompt capture has a separate privacy/retention contract, and a missing baseline cannot establish prior section values. Cross-process continuity is not required for this bounded comparison.

### Producer and call-site scope

| Production system-prompt producer | Current assembly/call path | Scope |
|---|---|---|
| Interactive conversational and loop-profile executor | `ContextBuilder`; `AgentLoop` and `SubagentManager` | Included; baseline owner is the logical interactive session or bridge cycle respectively. The executor's step-position updates are observed in the final system-message bytes; post-fit `system_context` content is omitted as unknown/sensitive without any structural signal. |
| Proposer, demand-proposer, goal-review, ranked proposer, multi-proposer | `role_prompt` via the direct SDK call paths in `runtime.llm_proposer` (`propose`, `maybe_propose_ranked`, `propose_multi`); `propose` selects goal-review when passed its system prompt | Included; correlate each logical invocation with applicable existing call, prompt, and bounded provider-failure telemetry. |
| Planner | `role_prompt` via bridge `SubagentManager` fixed-role prompt path and provider choke point | Included; separate planner producer/schema baseline and telemetry component within its bridge cycle. Other generic fixed-role `SubagentManager` bypass callers are excluded; their supplied prompt is not assumed to be planner schema. |
| Reflector | `role_prompt` via `runtime.reflector` direct SDK client | Included; one reflector job is the owner window; repeated cycle prompts share its reflector producer/schema baseline. |
| Strategist | `role_prompt` via `runtime.strategist` direct SDK client | Included; standalone invocation, one-snapshot baseline. |
| Curator | `role_prompt` via `runtime.knowledge_curator` direct SDK client | Included; one curator job is the owner window; repeated lesson batches share the curator producer/schema baseline. |
| Narrator | `role_prompt` via `scripts.journal_story` direct SDK client | Included; standalone invocation, one-snapshot baseline. |
| Skill-eval, persona harness, knowledge-lift, memory-consolidation, generic fixed-role `SubagentManager` bypass callers, and arbitrary provider callers | Evaluation or generic call paths; not all use named autonomous-role telemetry | Excluded from this ADR's coverage claim. Existing prompt behavior is unchanged; inclusion requires an explicit future scope and tests. |

This table identifies named production role paths, not every LLM request in the repository. `ContextBuilder` and `role_prompt` currently return assembled strings; section metadata must be derived at their existing assembly boundary without parsing delimiter text. Executor position updates are included only as exact final system bytes under a separately approved section classification; absent that approval they are omitted without disclosing structure. Any post-fit `system_context` append is unknown/sensitive and omitted without a presence signal. Provider/prompt telemetry is best-effort: if a call or predecessor row is absent, consumers treat affected provenance as unavailable, never as a complete history. The existing call `seq` remains legacy telemetry and is not upgraded into an identity. Per-owner in-memory comparison state is bounded and evictable; an eviction resets the baseline and requires a full snapshot, not an inferred continuation.

# Rollback

Remove the optional provenance fields and in-memory baseline cache; existing call and prompt readers continue to consume legacy rows. Existing raw prompt records, call counters, role prompts, and prompt assembly are not migrated or rewritten. No prior history is reconstructed after rollback.
